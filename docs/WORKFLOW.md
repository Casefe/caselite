# CaseLite｜律师与 LLM 协作开发手册

## 原型直接开发模式｜2026-11-05

用户已授权：安全测试完成后直接在CaseLite主开发文件夹写入，产品未完成前不要求GitHub分支合并记录，优先快速实现产品功能。本节为当前手动/Codex会话执行方式，覆盖下文旧流程的专用分支、worktree、Draft PR、远端CI/合并作为本地交付前置，以及完成一项后等待再次开工批准的要求。外置Runner已有部分限定profile的真实证据，按第6节核对；不作为当前产品开发的前置，也没有因此启用常驻执行器。

既有R0专项授权（当前旧队列新开工和自动推进按下述调度更新冻结）：R0全部任务原按依赖串行自动推进，工程客观DoD满足可改已完成，需要人工接收则待验收；允许同步CaseLite主目录、GitHub本地checkout与开发分支。每轮仍核对当前用户授权，不将该历史专项授权扩大到其他任务的状态写回或远端操作。不据此自动合并高风险改动到main、发布或调用收费Provider。仅在明确额度中断且旧进程已终止时按30分钟安排恢复，回执未知先查；暂停时不另启任务。授权本身不是Runner实现或实测证据。

1. 读取当前Issue、必要合同及代码，核对checkout/HEAD和未提交修改；单写入者沿用现有开发目录，不自动切main、重置、清理或覆盖他人修改。
2. 先核验当前HEAD的适用安全检查。已有同代码/规则/依赖/环境证据可复用；变化使证据失效时补测。通过后直接写目录中的获准文件，不等待新分支、PR或GitHub合并。
3. 按用户可见结果做最小实现。UI必须提供实际操作证据；数据/恢复做必要失败与重启验证；普通文档/样式改动按实际影响检查，不反复运行无关测试。不为追求速度删除失败测试、权限检查或保存确认。
4. 修改后运行受影响检查；安全边界、依赖、公开资料等变更补安全基线。每个可复核结果保留准确Diff、测试/运行证据与回退方法；本地提交、推送和合并均按 AGENTS.md 当前规则分别取得明确授权。
5. 回读Linear逐项核对Done条件。纯工程工作满足适用测试/证据/复核后按用户授权更新状态；需要业务/体验接收的工作提供具体可看成果。已确认场景不重复确认，设计通过不算产品运行通过。
6. 当前会话完成一张后交付证据并停止该卡写入；旧队列不自动开工或推进。本轮主控明确派发的获准任务按下述调度执行。遇到新的业务选择、费用、材料外发、不可逆操作或缺少必要接收时，只暂停依赖该决定的动作。

产品原型阶段保留的最低保护：不提交秘密/真实客户材料、不覆盖原件及已保存修订、不把内存状态当落盘成功、不让Renderer绕过受控Application直写数据库。必要的高风险技术复核仍适用；既有本地测试不等于未来完整安全审计。未来重写是待评估选择，不假设必然重写。

交付向用户说明功能结果、关键测试与可看证据，GitHub历史不用作用户阅读门槛。公开发布须经过本页产品与发布门禁。

## 1. 每轮只选一个 Linear Issue

ChatGPT负责需求澄清、规划和解释证据，律师决定业务含义、批准与验收；Linear保存任务、合同、依赖和批准；Codex负责开发与命令执行；GitHub保存代码、PR、CI和合并证据。可左侧ChatGPT规划、右侧VS Code/Codex观察与审阅，终端运行Codex CLI和检查；VS Code/Cursor不是自动执行依赖，也不让两个编码会话同时改同一任务。

由律师在Linear批准一个清晰的用户结果、Owner、范围和验收标准。LLM 开工时先核对实际仓库及对应 Issue；若依赖、入口、配置或授权不足，提出明确阻塞，不随意变成其他任务。

每个开发对话实施1项；一个PR服务一个主要Issue，复杂Issue允许少量顺序PR，中间PR不等于整项完成。长期Issue保留结果/Owner/边界/验收；实施卡只记录本次合同修订、baseline SHA、批准范围、真实依赖产物、允许文件、API/Schema/状态、样本/反例、命令、回退与未测项。普通文档小修无需另建计划文件。

开工前把每条获准验收条件写成可观察的通过与失败结果，列正常、反例及适用恢复样本、证据入口和人工接收点；模糊目标先收敛到本次用户结果，不能由 AI 自行扩大为性能、样式或架构优化。实现切片只领取能独立核对的一组条件，并写明允许文件和非目标；完成一个切片不等于整卡验收。

当前技术栈和调用边界以 [ARCHITECTURE](./ARCHITECTURE.md)、现行02及实际锁文件为准。关键新选型先比较维护状态、文档和社区资料、同类业务的可核查落地案例、许可证、现有基建适配及退出路径；在原 Issue 的最小方案中给出轻量调用/数据边界，长期或跨稳定边界决定按需写 ADR 和 Spike。不得在实施中暗换技术栈或凭热度引入框架；证据不足时保留现有方案并交 Owner 决定。

## 2. 标准七步

1. **只读预检**：读取当前Issue全文、适用合同章节、根及目标目录生效的 `AGENTS.md`、必要代码/API/测试；核对分支、HEAD、main、工作区与依赖实际产物。记录合同修订及批准范围，不覆盖其他未提交修改。
2. **最小计划**：复述目标、将修改的文件、不会修改的范围、风险、测试和回退；影响业务/数据/安全/外发/费用的决定由律师确认。
3. **最小实现**：按当前直接开发授权沿用现有checkout，单写入Owner、最小 diff；破坏性演练使用隔离测试数据。不顺手迁移全局技术栈，不安装“可能以后用”的框架；重要实验可放独立临时目录，不得让产品依赖它的路径。
4. **机械检查**：从 `package.json` 和 [DEVELOPMENT](./DEVELOPMENT.md)核实命令；运行适用类型、lint、单元/合同、安全与准确Diff检查，记录退出码和脱敏日志。文档同样核对来源、路径/链接和过期执行规则。
5. **回归与PR/CI**：依影响跑集成、真实Electron、构建及恢复，无法运行逐项记明。授权允许时提交专用分支、推送并用现有PR模板创建Draft PR；核对当前head SHA的必要CI及适用独立审查。CI不替代桌面测试或业务验收。
6. **人工验收**：律师看本次文档产物或实际界面/行为与业务结果，选择接受、退回或暂停；法律结论/客户外发须明确确认。
7. **交接与版本**：列出合同/批准、分支/当前SHA、文件、实际检查/退出码、适用PR/CI、失败/未测、风险、回退和唯一下一安全动作；按本次授权维护现有Issue/PR记录。完成后回读真实依赖、停写交主控，旧队列不自动推进；本轮主控明确派发的获准任务按当前调度执行；合并、发布、Linear写回各自核对权限，不扩大批准范围。

涉及开源采用时按需检查 [开源采用矩阵](https://linear.app/logixy-ai/document/研究参考caselite开源架构参考与采用矩阵-v11-c4cdac98fa55)、相关 ADR 与当前 Issue。参考项目的流行度不是技术或许可证明；发现许可证未知、AGPL／商业代码复用、隐性兼容或新增核心框架时，按 `AGENTS.md` 的准入条件停止。

## 逐项确认与代理执行（DEV-1924）

围绕一个获准 Issue，主控复用现行合同与已批准方案；复杂方案由 Sol High 补足用户结果、边界、失败和回退，再由独立 Sol High 上下文核对。实施模型按 [AGENTS.md 当前路由](../AGENTS.md#当前模型与-git-权限2026-11-15-用户更新)选取；同一切片第 4 次有效开发失败按 DEV-1926 自动升级，旧 Terra 两轮上限不再适用。每项交付由独立 Sol High 上下文核对实际 Diff、测试和风险，输出可操作的结果与证据。已确认事项不重复询问，无法验证的环节如实保留待验。

### 主控与单 Issue 调度（DEV-1924）

2026-11-15 用户更新：冻结旧队列的新开工与自动推进；仅本轮主控明确派发的获准任务例外。主控分析可开发任务、优先安排当日事项，只统筹和协调，不承担具体实现或返修。每个新开发任务新建一个对话，一个对话只协调一个获准 Issue；具体实现与返修由作者子智能体执行，另一独立 Sol High 上下文按实际需求、准确 Diff、测试和失败路径审查。使用现有 Codex 对话和子智能体入口，不据规则文字推断宿主强制隔离或自动后台调度已实现。

在途任务保全至安全检查点；未知提交或回执先核对，不强杀未知状态操作，主控交流不打断在途任务。隔离候选在批准边界内可并行，公共源码、协议、Schema、规则、Node、Build 和 ABI 的接合及共享写入由单写入者串行。候选完成后停写交主控，公共接合先取得执行槽并重核当前差异和证据。冻结不取消需求，也不强制停止无关研究；旧队列须用户明确恢复后才继续。静默测试、Git commit、push、merge 的分别授权及其他既有边界继续有效。

### 静默测试与批次授权

2026-11-15 主控用户更新，归口 DEV-1924：开发所需测试默认静默运行，不打断用户电脑操作。

- 能后台执行的 Node、类型、单元、合同、SQLite、jsdom 等检查优先后台运行，采用低优先级（nice 10）和有界并发；不得以删除测试或放宽超时换取安静。
- 不抢前台、键鼠、焦点、输入法或剪贴板；未获用户本轮明确安排，不自动打开、关闭或重启用户 App/浏览器；不触发系统凭据授权弹窗，不热替换当前运行的验收包或切换工作区。
- 会打开桌面或争用输入的 native、E2E 和 package probes 先记 `NOT_RUN`，等待用户明确安排前台批次；不逐卡反复请求暂停。旧的原生测试暂停授权不扩展到本次新禁令。
- 已有同范围、目的、数据、预算及权限的授权持续复用；一次批次授权覆盖该批次内的测试。新费用、敏感材料的新目的地或用途、权限扩大、不可逆数据操作及 Git commit、push、merge 仍按既有规则分别明确授权。
- 测试授权不扩为无限操作；如实记录未测项及其对交付和验收的影响，不能以后台检查替代必需的真实桌面验证。

### 失败计数与模型调用（DEV-1926）

主控为同一 Issue 的同一最小切片逐次记录候选 Diff/测试或审查证据、失败原因、实际模型、**当前档位有效开发失败数**及总失败数。只有新候选在真实功能、安全或独立审查门禁中失败才给当前档加一；同一命令的重复运行不加一，基础设施、测试环境、认证、网络及额度故障分开记录。失败后先定位根因并提出有变化的下一尝试；相同错误连续两次且无新证据时，先缩为最小复现或改变方案，不能为触发升级制造第四次失败。

当前档位计数达到 4 时，不再让原实施者写入：核对 Issue 批准、当前 HEAD、准确 Diff、工作区 Owner、在途进程、未知回执、用量与模型可用性，留下可恢复交接。随后通过宿主可指定模型的子任务入口，或已验证且获准的 Codex CLI/SDK profile，**只启动一次**目标模型：Terra medium → Sol high，Sol medium/high → Astra high。目标模型从交接和原 Issue 继续同一切片，原上下文不得同时写入；目标档位从 0 次重新计数，原档第 4 次失败不再触发下一档，总失败数保留供诊断。成功仍须另一独立 Sol High 审查和原测试/业务门禁。Astra high 失败、目标模型不可用、额度/费用边界不明或启动回执未知时保留现场并报告，不重复启动、购买额度或换外部模型。

当前外置 Runner 只验证了合成文档 profile；本规则不能使其自动支持产品代码或规则文件。若宿主没有已验证的指定模型调用入口，该切片记 `BLOCKED`，自动调用记 `NOT_RUN`。新模型、权限或工具配置生效前执行 [独立回归](./REVIEW_HANDOFF_EXERCISE.md)；模型规则的可读性、模拟计数、真实指定模型启动和产品交付分开记录。

用户确认产品方案及新的业务/法律含义、关键架构或拟复用源码、实际界面体验、真实客户资料启用与公开发布。费用、权限、资料外发、不可逆操作及 Git commit、push、merge 继续按现行授权分别处理；未获授权时暂停依赖该决定的动作。设计、工具报告与工程检查均不代替律师在真实入口的业务验收。

当前产品实现仍按一个 Issue、单写入者串行。工作树可供隔离研究、夹具或审查；运行 Electron 负向或恢复演练前，实证独立 userData、SQLite、原件及附件目录，并按需隔离缓存和凭据命名空间。隔离未验证时不执行破坏性样例。

外部 Skill 与开源工具须有具体消费者，先按现行06、DEV-1569 及 ADR-005 核对来源、许可、行为、依赖与退出路径；Knip、Storybook 和外部 UI Skill 仅为候选，不因列名自动安装或准入。Knip 所标 ISC 不在本仓当前生产依赖 MIT/Apache-2.0 许可门禁内，适用范围及政策须先核实。CaseLite 已确认的主题与交互优先于通用 Skill 风格；浏览器组件报告不能代替真实 Electron 及恢复验收。

## 代码精简与复用的必备检查（DEV-1931）

每卡开工／交付、开发期间每周候选检查及发布候选冻结前，执行 [CODE_HYGIENE](./CODE_HYGIENE.md) 的适用步骤，沿本页七步和原 Issue 记录复用、保留／候选、消费者、清理前后测试及回退。不因周期检查自动领取任务或删除代码；索引生成器、定时任务及检查器接入尚未实现。规范正文的额外hash绑定与独立回归沿其交付边界执行。

## 代码保护与受控变更（DEV-1935）

沿本页既有步骤执行[CODE_PROTECTION](./CODE_PROTECTION.md)，在原Issue补充资产等级/动作及裁决依据、消费者分类与未知项、源码可写和运行副作用范围。首次写/迁移前核验真实profile/路径及隔离，最终验证使用全程稳定输入并绑定实际产物；无法证明则保留有限证据并阻断最终放行。按本次影响定义正常/失败/恢复断言，独审核对后交付；不另建Runner、任务账本或逐命令审批。新规范及CODE_HYGIENE的额外hash/精准Diff、既有fresh回归和带回执检查按其机械边界执行，未实现自动保护如实记录。

## 十二项开发机制的执行对照

以下把 [The AI-native SDLC playbook](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) 的做法落实到已有机制；只参考方法，没有复用源码。这是本仓库必须执行的开发约定，不是另一套流程。每卡按实际风险选用既有入口；相同证据可被多项引用，不要求另建文档或十二份检查表。

| 机制                   | 既有入口与必须执行的动作                                          | 交付依据                                                |
| ---------------------- | ----------------------------------------------------------------- | ------------------------------------------------------- |
| 1. 明确意图            | 当前Linear Issue写清唯一用户结果、Owner、范围与验收               | 实时Issue及本轮批准，不从标题猜范围                     |
| 2. 需求和设计先明确    | 现行合同＋最小计划明确输入输出、边界、失败与回退；长期决定按需ADR | 合同修订、正反样本，未批准业务含义停止                  |
| 3. 计划后实施          | 本文标准七步：预检、已有实现检索、最小改动                        | baseline、允许文件、真实依赖；单卡串行                  |
| 4. 项目规则可发现      | 根/目录AGENTS与SOURCES按需加载                                    | 实际读取路径；变更后新上下文实测                        |
| 5. 团队知识可复用      | 复用已有文档、ADR、操作单和获准Skill                              | 修复既有Owner入口；不重复建设规则库或Skill              |
| 6. 合适的协作与上下文  | 单写入者实现，受保护或高风险变更由独立上下文审查                  | 独立审查的输入、发现、未测项；不并发改共享文件          |
| 7. 给开发Agent真实反馈 | 现有quick及受影响集成、Electron、恢复测试                         | 命令、退出码、原始证据；Mock与真实运行分开              |
| 8. 持续回归开发Agent   | 既有REVIEW_HANDOFF_EXERCISE的三个固定场景                         | 规则/模型/权限/检查器变化或错误复发须重验；有效回归回执 |
| 9. 持续审查准确差异    | CODE_REVIEW＋review:changes保护规则、测试与CI                     | 精准diff及独立结论；不能删保护换绿色                    |
| 10. 动作前机械门禁     | 现有命令/CI阻断可识别违规；有回归触发时执行带回执的交付检查       | 缺失/过期/非真实回归exit 1；权限和业务判断仍按批准      |
| 11. CI/CD与受控自动化  | 当前直接开发＋必要CI；外置Runner只在已验证profile及本次授权内用   | 本地提交或同SHA远端证据；不把CI/合并当业务接受          |
| 12. 效果与失败反馈     | 原Issue交接记录耗时、返工、用量；复用现有质量证据回顾             | 实际可得数据，未知写UNKNOWN；重复失败回到原Owner修复    |

交付必须能沿本表找到适用证据；不适用项在现有交接中说明理由。检查失败、适用独立审查/回归缺失时不得宣称完成。机器可判断的项目由现有检查阻断；自然语言范围、法律/业务接受及实际会话独立性须由相应Owner/审查者核对，不能以一段提示词保证遵守。

## 4. 人工决策的最小表

| 结果 | 判断依据                                               | 下一动作                              |
| ---- | ------------------------------------------------------ | ------------------------------------- |
| 接受 | 达到本次产物/用户可见结果、适用技术审查及测试/安全要求 | 明确接受范围；按另行授权合并/记录Done |
| 退回 | 目标不满足、证据不足或出现回归                         | 只修复缺口，补相关测试                |
| 停止 | 数据/权限/费用/法律效果不确定，或不可逆变更            | 暂停并给出候选方案和风险              |

例如：范围和回退清楚、真实命令已找到，可判断「计划可开始」；只看到 AI 自评或模拟结果，判断「证据不足，退回补验」；涉及资料外发、收费、权限或法律结果，判断「需要律师决定，停止等待」。未运行的测试不得写通过，模拟结果不得写联调完成。

验收前再看三件事：LLM 是否把参考代码的热度当作正确性证据，是否把模拟当成真实 Spike，是否通过删除测试或放宽架构检查取得绿色结果；任一项为是，先退回或停止。

## 4.1 常见失败如何处理

| 情形                               | 操作                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| 上下文不足或来源冲突               | 重新读取当前 Issue、仓库文件及必要 Resource；指出具体冲突，暂停依赖该事实的修改。   |
| 编造 API、命令或目录               | 在当前源码、`package.json` 和锁文件中核实；不存在就报告，不以猜测补齐。             |
| 重复模块或过度设计                 | 先搜索旧入口与合同，缩回本 Issue 的最小改动；新增核心依赖或长期协议先走 ADR/Spike。 |
| 命令或 CI 失败                     | 保留原始退出码和日志，定位原因、修复后重跑；不得删除测试或弱化门禁换绿色。          |
| 需要未经授权的联网、代码复用或外发 | 停止相关动作，说明接收方、资料范围、费用和许可证，待律师确认。                      |
| 无法证明完成                       | 列出通过、失败、未运行及缺失证据；退回补验或暂停，不能凭 AI 自评接受。              |

返工仅修复已发现的缺口并重跑相关检查。未提交的错误修改先核对 `git diff` 和归属，只在明确授权后定向恢复本任务文件，不能覆盖其他修改；已提交的改动优先用新提交撤销，涉及迁移或用户数据时先按恢复合同处理，不能直接删除旧数据。

同一失败连续两轮没有新增证据时，转最小复现/定位并缩小问题，提出复用、缩减或替代方案，不扩大改动或无限重试；影响合同或关键架构的方案提交相应 Owner 决定。额度/认证/网络失败先保留现场；工具用量可见才记录，不可得记 `UNKNOWN`。Codex订阅额度、其他工具费用与CaseLite产品API费用分别记录，不虚构固定Token配额，不自动换付费Provider重放任务。

两轮无新证据后的交接在原 Issue/本轮证据中附：触发步骤与输入条件、预期和实际结果、原始脱敏报错及退出码、最近准确 Diff/当前 SHA、已试方案及各自结果、最小复现、仍未知项和唯一下一安全动作。先区分产品缺陷与环境/认证故障；这些信息用于定位和求助，不替代 DEV-1926 的有效失败计数或擅自触发模型升级。

## 4.2 在既有证据中复盘效果

完成一批获准工作或同类错误复发时，运行现有 `pnpm evidence` 查看本机质量记录的派生汇总，再在原 Issue 的交接/复核中记录判断。汇总按模式、工具版本、平台、依赖指纹和检查计划分组，保留原文件链接；旧记录缺快照单列，坏记录明确报错，不重写原证据。历史失败频次用于找修复入口，不表示当前仍失败；重复跑检查不等于完成更多任务，检查耗时也不等于端到端交付时间。

每卡沿用现有交接字段记录：用户结果/接受证据、开始至可审查交付的时间、等待审查时间、人工返工次数及原因、实际可得的工具用量/费用；不可得统一写 `UNKNOWN`，不估造，也不披露非公开成本或敏感数据。开发工具费用与产品Provider调用分开。没有同类任务/同样本和同口径基线，不宣称效率提升。重复错误回到原Owner的现有规则、测试或实现补最小反例；已有机制表现良好就保持。不得为统计另建任务台账、评测平台或常驻任务。

## 5. 交接不等于复制聊天

长期技术选择写进 ADR，稳定产品规则在产品/架构资源中，真实代码位置和命令由仓库负责；Issue 状态仍由 Linear 管理。新一轮 LLM 不能依赖“我在上一段聊天解释过”。交接还须写明采用的参考来源、Commit、许可证处理、实际运行和未运行内容及回退点；没有参考代码时明确写「无」。

跨会话所需的三类信息已有唯一入口：项目总览及真实启动方式见 [README](../README.md)，稳定架构和技术栈见 [ARCHITECTURE](./ARCHITECTURE.md)/ADR，当前进度、批准与下一动作见实时 Linear Issue 和本轮证据。交接只提供这三类入口及本次差异，不另建会过期的进度文件，也不把历史方案当当前状态。

如果文档与代码不一致，首先查实际迁移、锁文件、运行结果及最新 Linear；明确冲突供人决策，不默默改写现有事实。

每批获准工作收口或相关实现变化时，核对受影响文档的 Owner、来源修订、路径/链接、实际命令及能力声明；失效内容回原 Owner 修订，历史证据标明当时范围，不批量删除。周期性复盘沿用现有 Issue 和证据，不创建平行账本。

## 6. 受控自动化（按已验证 profile 使用）

外置Runner的限定profile已有真实执行与平台回写证据，入口见 [Runner证据读取与恢复](./architecture/dev-runner-evidence.md)及DEV-1694—1697的当前记录。必须核对具体profile、run、批准、允许路径、命令和未测项；小范围文档或专项试点通过不代表所有产品卡、恢复路径或常驻队列均已验证。启用新profile前仍须在实际环境完成适用正反联调；自动化不作为手动受控开发的额外前置。开发Runner放在产品仓库外，与CaseLite内置Agent/MCP分开，不增加第二任务数据库或CI平台。

**批准与领取**：Runner仅领取“已明确，可开发”且有本次明确外置批准的Issue。“待排期”、高优先级或旧聊天均不是授权。批准绑定Issue/team/project、描述指纹、合同修订、baseline SHA、允许/禁止路径、必需命令及是否允许自动合并；执行前后回读依赖产物、批准、状态、归档与权限。变化即停止；不修改父子/里程碑或其他任务。Codex worker不持有Runner的Linear写回/合并凭据，不自行改批准条件。手动路径沿用本次明确授权，不假装已取得Runner锁。

**记录与状态**：每run在目标Issue维护一条主开发评论，记录领取/基线、实现/本地检查、PR/CI、失败/交接；普通命令只写产品仓库外有界脱敏journal，不逐命令刷评论。评论和状态写回必须被本次配置授权。评论是人读摘要，journal是机器恢复依据；写前记录待发送事件，回执不明先查同run/comment/PR ID，避免重复评论、PR或模型启动。结果统一用 `PASS_REAL/MOCK_ONLY/NOT_RUN/BLOCKED/FAIL`。

本地通过但PR/CI或必要证据不完整时保持开发中。只有本地真实检查、当前PR同SHA全部必要CI成功、批准有效且交接可核查，才由1695推进待验收；空/缺检查、旧SHA、pending/failure/canceled/skipped、分页不全/部分错误均阻断，N/A须预先批准。写前后回读，人工改状态/撤回批准则停止；API无原子CAS时记录竞争限制。执行器与GitHub原生集成只能有一个状态推进Owner，必须核对实际设置，不能让“合并即Done”绕过律师验收。

**推分支、合并和发布**：已明确授权的独立分支推送及Draft PR可自动执行；未授权时交付本地结果等待批准。自动合并另需本次批准快照显式 `autoMergeAllowed=true`、低风险允许路径、当前PR已转Ready、最新同SHA必要检查、适用审查及验收全部满足，并核对GitHub真实规则、base/ref和合并状态。高风险或未知、分支落后/冲突、新提交未测、缺审查或规则/权限改变均停止。SQLite/迁移、原件/Anchor、Y.Doc/恢复、密钥/权限、依赖/锁文件、许可证、安全/测试/CI门禁、构建/发布、业务含义或不可逆操作禁止自动合并；需要业务操作验收的任务须有接受证据。本次规则文件修复不能自行按低风险自动放行。

合并响应未知先查GitHub；成功后读取实际PR状态和merge commit，若评论未回写只补原run，不重复合并。CI/合并只证明相应工程事实，不自动标记Issue“已完成”；Done仍需律师接受及适用独立复核等条件，按明确人为决定处理。产品发布、部署及直推main不由分支推送授权涵盖。

## 6.1 断点恢复与下一步

手动中断时把短交接保存在已有Issue/PR或当前交付位置。Runner启用后，其外置journal在关键写操作前后保存：`runId/issueId/team/project`、合同修订/批准指纹、baseline SHA、工作区、实际读取规则、工具/模型及可得用量或UNKNOWN、阶段/时间、当前SHA、命令/退出码/Mock分类、PR/评论ID、写回已确认/待确认、未测项、回退和 `nextAction`。日志不含客户材料、Key或敏感stdout；不入产品库，也不反解析评论来猜执行状态。

新会话先核对最新Issue/合同、适用AGENTS、当前HEAD和未提交Diff，再读取现有run/PR/CI/journal。优先确认或恢复旧run，回执未知先查询远端，不能盲重跑写操作或启动第二模型；批准/基线改变则交Owner决定。换会话前留下唯一下一安全动作，不能只说“继续上一段聊天”。

下一步从Linear实时数据筛选，核对批准、真实前置产物、当前main、未完成run/PR/业务验收、风险与共享文件冲突。输出“可领取/等待依赖/需律师批准/需返工/待业务验收”及原因，最多建议随后2—3项；建议不等于执行授权，不从NEXT.md、标题序号或历史聊天自动开工。无候选只报告阻塞，不构造任务、不无限轮询；常驻队列、批量/并发开发和自动跨Provider重试另行准入。

## 7. 代码可读性与独立审查（DEV-1562 / DEV-1564）

1. 开工按当前Issue加载适用 `AGENTS.md`、必要合同、代码和 [审查规范](./CODE_REVIEW.md)；报告已读取路径及适用约束。不要为每段代码创建注释。
2. 先检索已有实现，确认目标包、允许变更和禁止变更；结构、协议、持久化与权限调整须说明 ADR 准入。
3. PR 使用 `.github/PULL_REQUEST_TEMPLATE.md`，填写实际输入输出、关键风险、测试命令及结果、未运行项、回退方法；注释只解释重要的「为什么」。
4. 对安全、IPC、SQLite、PDF 原文定位、Yjs/同步和正式外发等关键变更，安排独立上下文审查；审查者必须阅读 diff、相关合同、实际测试证据，明确发现与剩余风险。审查者的自评不是门禁。
5. 合并前确认自动检查与 GitHub 分支保护真正生效。仅有 workflow 文件或报告不代表 branch protection 已启用；macOS 打包测试不能被 Linux CI 绿色结果替代。
6. 规则修改后用新会话核对实际加载路径及覆盖关系；链接不保证内容自动进入上下文。DEV-1564 的一次新会话实际交接演练按 `docs/REVIEW_HANDOFF_EXERCISE.md` 执行，留存命令、检查结果及未验证项；不得在演练中生成正式 Matter 产品实现；未运行演练记NOT_RUN，不以本次文档修改声称通过。worktree只隔离代码，Electron/负向恢复演练前须实证独立userData、SQLite、原件及必要缓存/凭据命名空间，未验证隔离不执行破坏样例。
