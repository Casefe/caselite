# CaseLite｜律师与 LLM 协作开发手册

## 原型直接开发模式｜2026-11-05

用户已授权：安全测试完成后直接在CaseLite主开发文件夹写入，产品未完成前不要求GitHub分支合并记录，优先快速实现产品功能。本节为当前手动/Codex会话执行方式，覆盖下文旧流程的专用分支、worktree、Draft PR、远端CI/合并作为本地交付前置，以及完成一项后等待再次开工批准的要求。外置Runner已有部分限定profile的真实证据，按第6节核对；不作为当前产品开发的前置，也没有因此启用常驻执行器。

既有R0专项授权：R0全部任务按依赖串行自动推进，工程客观DoD满足可改已完成，需要人工接收则待验收；允许同步CaseLite主目录、GitHub本地checkout与开发分支。每轮仍核对当前用户授权，不将该历史专项授权扩大到其他任务的状态写回或远端操作。不据此自动合并高风险改动到main、发布或调用收费Provider。仅在明确额度中断且旧进程已终止时按30分钟安排恢复，回执未知先查；暂停时不另启任务。授权本身不是Runner实现或实测证据。

1. 读取当前Issue、必要合同及代码，核对checkout/HEAD和未提交修改；单写入者沿用现有开发目录，不自动切main、重置、清理或覆盖他人修改。
2. 先核验当前HEAD的适用安全检查。已有同代码/规则/依赖/环境证据可复用；变化使证据失效时补测。通过后直接写目录中的获准文件，不等待新分支、PR或GitHub合并。
3. 按用户可见结果做最小实现。UI必须提供实际操作证据；数据/恢复做必要失败与重启验证；普通文档/样式改动按实际影响检查，不反复运行无关测试。不为追求速度删除失败测试、权限检查或保存确认。
4. 修改后运行受影响检查；安全边界、依赖、公开资料等变更补安全基线。每个可复核结果保留本地小提交、准确Diff、测试/运行证据与回退方法；提交不是发布，不自动触发远端推送。
5. 回读Linear逐项核对Done条件。纯工程工作满足适用测试/证据/复核后按用户授权更新状态；需要业务/体验接收的工作提供具体可看成果。已确认场景不重复确认，设计通过不算产品运行通过。
6. 当前会话完成一张后，自动选真实依赖已满足且范围已批准的下一张最小卡继续；未具备前置的卡留原因并寻找其他可推进项。遇到新的业务选择、费用、材料外发、不可逆操作或缺少必要接收时，只暂停依赖该决定的动作。

产品原型阶段保留的最低保护：不提交秘密/真实客户材料、不覆盖原件及已保存修订、不把内存状态当落盘成功、不让Renderer绕过受控Application直写数据库。必要的高风险技术复核仍适用；既有本地测试不等于未来完整安全审计。未来重写是待评估选择，不假设必然重写。

交付只向用户说明功能结果、关键测试与可看证据，GitHub历史不用作用户阅读门槛。公开发布前再按当时产品风险和实际团队需要建立分发/协作检查。

## 1. 每轮只选一个 Linear Issue

ChatGPT负责需求澄清、规划和解释证据，律师决定业务含义、批准与验收；Linear保存任务、合同、依赖和批准；Codex负责开发与命令执行；GitHub保存代码、PR、CI和合并证据。可左侧ChatGPT规划、右侧VS Code/Codex观察与审阅，终端运行Codex CLI和检查；VS Code/Cursor不是自动执行依赖，也不让两个编码会话同时改同一任务。

由律师在Linear批准一个清晰的用户结果、Owner、范围和验收标准。LLM 开工时先核对实际仓库及对应 Issue；若依赖、入口、配置或授权不足，提出明确阻塞，不随意变成其他任务。

当前实施1项、随后仅准备2—3项实施卡；一个PR服务一个主要Issue，复杂Issue允许少量顺序PR，中间PR不等于整项完成。长期Issue保留结果/Owner/边界/验收；实施卡只记录本次合同修订、baseline SHA、批准范围、真实依赖产物、允许文件、API/Schema/状态、样本/反例、命令、回退与未测项。普通文档小修无需另建计划文件。

## 2. 标准七步

1. **只读预检**：读取当前Issue全文、适用合同章节、根及目标目录生效的 `AGENTS.md`、必要代码/API/测试；核对分支、HEAD、main、工作区与依赖实际产物。记录合同修订及批准范围，不覆盖其他未提交修改。
2. **最小计划**：复述目标、将修改的文件、不会修改的范围、风险、测试和回退；影响业务/数据/安全/外发/费用的决定由律师确认。
3. **最小实现**：按当前直接开发授权沿用现有checkout，单写入Owner、最小 diff；破坏性演练使用隔离测试数据。不顺手迁移全局技术栈，不安装“可能以后用”的框架；重要实验可放独立临时目录，不得让产品依赖它的路径。
4. **机械检查**：从 `package.json` 和 [DEVELOPMENT](./DEVELOPMENT.md)核实命令；运行适用类型、lint、单元/合同、安全与准确Diff检查，记录退出码和脱敏日志。文档同样核对来源、路径/链接和过期执行规则。
5. **回归与PR/CI**：依影响跑集成、真实Electron、构建及恢复，无法运行逐项记明。授权允许时提交专用分支、推送并用现有PR模板创建Draft PR；核对当前head SHA的必要CI及适用独立审查。CI不替代桌面测试或业务验收。
6. **人工验收**：律师看本次文档产物或实际界面/行为与业务结果，选择接受、退回或暂停；法律结论/客户外发须明确确认。
7. **交接与版本**：列出合同/批准、分支/当前SHA、文件、实际检查/退出码、适用PR/CI、失败/未测、风险、回退和唯一下一安全动作；按本次授权维护现有Issue/PR记录。完成后按直接开发授权回读真实依赖，继续下一张已获准最小任务；合并、发布、Linear写回各自核对权限，不扩大批准范围。

涉及开源采用时按需检查 [开源采用矩阵](https://linear.app/logixy-ai/document/研究参考caselite开源架构参考与采用矩阵-v11-c4cdac98fa55)、相关 ADR 与当前 Issue。参考项目的流行度不是技术或许可证明；发现许可证未知、AGPL／商业代码复用、隐性兼容或新增核心框架时，按 `AGENTS.md` 的准入条件停止。

## 十二项开发机制的执行对照

以下把 [The AI-native SDLC playbook](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) 的做法落实到已有机制；只参考方法，没有复用源码。这是本仓库必须执行的开发约定，不是另一套流程。每卡按实际风险选用既有入口；相同证据可被多项引用，不要求另建文档或十二份检查表。

| 机制                   | 既有入口与必须执行的动作                                          | 交付依据                                                |
| ---------------------- | ----------------------------------------------------------------- | ------------------------------------------------------- |
| 1. 明确意图            | 当前Linear Issue写清唯一用户结果、Owner、范围与验收               | 实时Issue及本轮批准，不从标题猜范围                     |
| 2. 需求和设计先明确    | 现行合同＋最小计划明确输入输出、边界、失败与回退；长期决定按需ADR | 合同修订、正反样本，未批准业务含义停止                  |
| 3. 计划后实施          | 本文标准七步：预检、已有实现检索、最小改动                        | baseline、允许文件、真实依赖；单卡串行                  |
| 4. 项目规则可发现      | 根/目录AGENTS与SOURCES按需加载                                    | 实际读取路径；变更后新上下文实测                        |
| 5. 团队知识可复用      | 复用已有文档、ADR、操作单和获准Skill                              | 修复既有Owner入口；不重复建设规则库或Skill              |
| 6. 合适的协作与上下文  | 单写入者实现，受保护或高风险变更由独立上下文审查                  | 独立审查的输入、发现、未测项；不并发改共享文件          |
| 7. 给开发Agent真实反馈 | 现有quick及受影响集成、Electron、恢复测试                         | 命令、退出码、原始证据；Mock与真实运行分开              |
| 8. 持续回归开发Agent   | 既有REVIEW_HANDOFF_EXERCISE的三个固定场景                         | 规则/模型/权限/检查器变化或错误复发须重验；有效回归回执 |
| 9. 持续审查准确差异    | CODE_REVIEW＋review:changes保护规则、测试与CI                     | 精准diff及独立结论；不能删保护换绿色                    |
| 10. 动作前机械门禁     | 现有命令/CI阻断可识别违规；有回归触发时执行带回执的交付检查       | 缺失/过期/非真实回归exit 1；权限和业务判断仍按批准      |
| 11. CI/CD与受控自动化  | 当前直接开发＋必要CI；外置Runner只在已验证profile及本次授权内用   | 本地提交或同SHA远端证据；不把CI/合并当业务接受          |
| 12. 效果与失败反馈     | 原Issue交接记录耗时、返工、用量；复用现有质量证据回顾             | 实际可得数据，未知写UNKNOWN；重复失败回到原Owner修复    |

交付必须能沿本表找到适用证据；不适用项在现有交接中说明理由。检查失败、适用独立审查/回归缺失时不得宣称完成。机器可判断的项目由现有检查阻断；自然语言范围、法律/业务接受及实际会话独立性须由相应Owner/审查者核对，不能以一段提示词保证遵守。

## 3. 一个可复用的任务指令

```text
当前仅处理 Linear Issue：DEV-____。
先只读检查当前 Issue 全文、合同修订、根及目标目录生效的 AGENTS.md、
Git 分支/HEAD/main/工作区、依赖实际产物和相关代码，
仅在本 Issue 需要时读取 docs/ 中有关产品、架构、测试或合同的文件。

请先给出：
1. 唯一用户结果和验收方法
2. 修改范围与明确非目标
3. 重要技术/安全风险和需要我决定的事项
4. 将执行的真实命令、失败路径和回退方法
5. 开源参考的来源、许可证及拟复用范围（没有则写「无」）

先运行适用的现有基线；批准范围内再实施最小修改，不得调整无关模块或削弱测试。
按影响范围完成回归；未运行的检查逐项说明原因，不能写成通过。
交付：修改清单、实际检查输出、未执行项、示例/截图（不含秘密）、回退方法。
本次授权：填写是否允许独立分支推送、Draft PR、评论/有限状态写回；默认不含合并或发布。
已明确批准的动作无需重复询问；授权不清、合同/范围改变则停止。
不直推 main，不擅自删除旧数据、改权限、外发资料或将 Issue 标记已完成。
```

## 4. 人工决策的最小表

| 结果 | 判断依据                                               | 下一动作                              |
| ---- | ------------------------------------------------------ | ------------------------------------- |
| 接受 | 达到本次产物/用户可见结果、适用技术审查及测试/安全要求 | 明确接受范围；按另行授权合并/记录Done |
| 退回 | 目标不满足、证据不足或出现回归                         | 只修复缺口，补相关测试                |
| 停止 | 数据/权限/费用/法律效果不确定，或不可逆变更            | 暂停并给出候选方案和风险              |

例如：范围和回退清楚、真实命令已找到，可判断「计划可开始」；只看到 AI 自评或模拟结果，判断「证据不足，退回补验」；涉及资料外发、收费、权限或法律结果，判断「需要律师决定，停止等待」。未运行的测试不得写通过，模拟结果不得写联调完成。

验收前再看三件事：LLM 是否把参考代码的热度当作正确性证据，是否把模拟当成真实 Spike，是否通过删除测试或放宽架构检查取得绿色结果；任一项为是，先退回或停止。

## 4.1 常见失败如何处理

| 情形                               | 操作                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| 上下文不足或来源冲突               | 重新读取当前 Issue、仓库文件及必要 Resource；指出具体冲突，暂停依赖该事实的修改。   |
| 编造 API、命令或目录               | 在当前源码、`package.json` 和锁文件中核实；不存在就报告，不以猜测补齐。             |
| 重复模块或过度设计                 | 先搜索旧入口与合同，缩回本 Issue 的最小改动；新增核心依赖或长期协议先走 ADR/Spike。 |
| 命令或 CI 失败                     | 保留原始退出码和日志，定位原因、修复后重跑；不得删除测试或弱化门禁换绿色。          |
| 需要未经授权的联网、代码复用或外发 | 停止相关动作，说明接收方、资料范围、费用和许可证，待律师确认。                      |
| 无法证明完成                       | 列出通过、失败、未运行及缺失证据；退回补验或暂停，不能凭 AI 自评接受。              |

返工仅修复已发现的缺口并重跑相关检查。未提交的错误修改先核对 `git diff` 和归属，只在明确授权后定向恢复本任务文件，不能覆盖其他修改；已提交的改动优先用新提交撤销，涉及迁移或用户数据时先按恢复合同处理，不能直接删除旧数据。

同一失败连续两轮没有新增证据时，转最小复现/定位并缩小问题，不扩大改动或无限重试。额度/认证/网络失败先保留现场；工具用量可见才记录，不可得记 `UNKNOWN`。Codex订阅额度、其他工具费用与CaseLite产品API费用分别记录，不虚构固定Token配额，不自动换付费Provider重放任务。

## 5. 交接不等于复制聊天

长期技术选择写进 ADR，稳定产品规则在产品/架构资源中，真实代码位置和命令由仓库负责；Issue 状态仍由 Linear 管理。新一轮 LLM 不能依赖“我在上一段聊天解释过”。交接还须写明采用的参考来源、Commit、许可证处理、实际运行和未运行内容及回退点；没有参考代码时明确写「无」。

如果文档与代码不一致，首先查实际迁移、锁文件、运行结果及最新 Linear；明确冲突供人决策，不默默改写现有事实。

## 6. 受控自动化（按已验证 profile 使用）

外置Runner的限定profile已有真实执行与平台回写证据，入口见 [Runner证据读取与恢复](./architecture/dev-runner-evidence.md)及DEV-1694—1697的当前记录。必须核对具体profile、run、批准、允许路径、命令和未测项；小范围文档或专项试点通过不代表所有产品卡、恢复路径或常驻队列均已验证。启用新profile前仍须在实际环境完成适用正反联调；自动化不作为手动受控开发的额外前置。开发Runner放在产品仓库外，与CaseLite内置Agent/MCP分开，不增加第二任务数据库或CI平台。

| 实施入口                                                | 唯一职责与启用条件                                                                                                                            |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| [DEV-1694](https://linear.app/logixy-ai/issue/DEV-1694) | 核对本次外置批准快照、加锁、隔离工作区，启动一次受限Codex CLI/SDK；固定本地检查、阶段记录、专用分支和Draft PR。失败保留现场，不自动领取第二项 |
| [DEV-1695](https://linear.app/logixy-ai/issue/DEV-1695) | 读取已有run及当前PR head，核对预先指定的必要Check Runs（名称＋App ID）同SHA真实成功，才按授权“开发中→待验收”；不重新启动Codex、不合并         |
| [DEV-1696](https://linear.app/logixy-ai/issue/DEV-1696) | 1694/1695真实联调后独立启用低风险受控合并；默认关闭，回查真实merge commit并更新原run记录，不自动Done或发布                                    |
| [DEV-1697](https://linear.app/logixy-ai/issue/DEV-1697) | 1695真实闭环后准入单线程候选筛选/恢复；默认只读建议，经明确批准后一次性复用1694；不要求先启用可选1696                                         |

**批准与领取**：Runner仅领取“已明确，可开发”且有本次明确外置批准的Issue。“待排期”、高优先级或旧聊天均不是授权。批准绑定Issue/team/project、描述指纹、合同修订、baseline SHA、允许/禁止路径、必需命令及是否允许自动合并；执行前后回读依赖产物、批准、状态、归档与权限。变化即停止；不修改父子/里程碑或其他任务。Codex worker不持有Runner的Linear写回/合并凭据，不自行改批准条件。手动路径沿用本次明确授权，不假装已取得Runner锁。

**记录与状态**：每run在目标Issue维护一条主开发评论，记录领取/基线、实现/本地检查、PR/CI、失败/交接；普通命令只写产品仓库外有界脱敏journal，不逐命令刷评论。评论和状态写回必须被本次配置授权。评论是人读摘要，journal是机器恢复依据；写前记录待发送事件，回执不明先查同run/comment/PR ID，避免重复评论、PR或模型启动。结果统一用 `PASS_REAL/MOCK_ONLY/NOT_RUN/BLOCKED/FAIL`。

本地通过但PR/CI或必要证据不完整时保持开发中。只有本地真实检查、当前PR同SHA全部必要CI成功、批准有效且交接可核查，才由1695推进待验收；空/缺检查、旧SHA、pending/failure/canceled/skipped、分页不全/部分错误均阻断，N/A须预先批准。写前后回读，人工改状态/撤回批准则停止；API无原子CAS时记录竞争限制。执行器与GitHub原生集成只能有一个状态推进Owner，必须核对实际设置，不能让“合并即Done”绕过律师验收。

**推分支、合并和发布**：已明确授权的独立分支推送及Draft PR可自动执行；未授权时交付本地结果等待批准。自动合并另需本次批准快照显式 `autoMergeAllowed=true`、低风险允许路径、当前PR已转Ready、最新同SHA必要检查、适用审查及验收全部满足，并核对GitHub真实规则、base/ref和合并状态。高风险或未知、分支落后/冲突、新提交未测、缺审查或规则/权限改变均停止。SQLite/迁移、原件/Anchor、Y.Doc/恢复、密钥/权限、依赖/锁文件、许可证、安全/测试/CI门禁、构建/发布、业务含义或不可逆操作禁止自动合并；需要业务操作验收的任务须有接受证据。本次规则文件修复不能自行按低风险自动放行。

合并响应未知先查GitHub；成功后读取实际PR状态和merge commit，若评论未回写只补原run，不重复合并。CI/合并只证明相应工程事实，不自动标记Issue“已完成”；Done仍需律师接受及适用独立复核等条件，按明确人为决定处理。产品发布、部署及直推main不由分支推送授权涵盖。

## 6.1 断点恢复与下一步

手动中断时把短交接保存在已有Issue/PR或当前交付位置。Runner启用后，其外置journal在关键写操作前后保存：`runId/issueId/team/project`、合同修订/批准指纹、baseline SHA、工作区、实际读取规则、工具/模型及可得用量或UNKNOWN、阶段/时间、当前SHA、命令/退出码/Mock分类、PR/评论ID、写回已确认/待确认、未测项、回退和 `nextAction`。日志不含客户材料、Key或敏感stdout；不入产品库，也不反解析评论来猜执行状态。

新会话先核对最新Issue/合同、适用AGENTS、当前HEAD和未提交Diff，再读取现有run/PR/CI/journal。优先确认或恢复旧run，回执未知先查询远端，不能盲重跑写操作或启动第二模型；批准/基线改变则交Owner决定。换会话前留下唯一下一安全动作，不能只说“继续上一段聊天”。

下一步从Linear实时数据筛选，核对批准、真实前置产物、当前main、未完成run/PR/业务验收、风险与共享文件冲突。输出“可领取/等待依赖/需律师批准/需返工/待业务验收”及原因，最多建议随后2—3项；建议不等于执行授权，不从NEXT.md、标题序号或历史聊天自动开工。无候选只报告阻塞，不构造任务、不无限轮询；常驻队列、批量/并发开发和自动跨Provider重试另行准入。
