# CaseLite｜律师与 LLM 协作开发手册

- **目标**：不要求律师阅读全部代码，也能验证 LLM 的任务范围、证据和可回退性。
- **来源**：[DEV-1562](https://linear.app/logixy-ai/issue/DEV-1562)、[DEV-1564](https://linear.app/logixy-ai/issue/DEV-1564)
- **状态**：建议操作规范，尚须在真实仓库用一次新会话预演。

## 1. 每轮只选一个 Linear Issue

由律师指定一个清晰的用户结果、范围和验收标准。LLM 开工时先核对实际仓库及对应 Issue；若依赖、入口、配置或授权不足，提出明确阻塞，不随意变成其他任务。

不是所有任务都需要长计划；修正文案与模块协议变更应使用不同的审查力度。

## 2. 标准七步

1. **只读预检**：查 `AGENTS.md`、`git status`、相关源文件和必要的 Linear 资源；记录基线版本。
2. **最小计划**：复述目标、将修改的文件、不会修改的范围、风险、测试和回退；影响业务/数据/安全/外发/费用的决定由律师确认。
3. **隔离实现**：最小 diff，不顺手迁移全局技术栈，不安装“可能以后用”的框架；重要实验可放 CASDEV `scratch/`，不得让产品依赖它的路径。
4. **机械检查**：执行真实存在的局部类型、lint、单元/合同和安全检查；记录原始输出。
5. **完整回归**：依影响范围跑集成、E2E、构建与故障恢复；无法运行就列出未验证项，不得说成功。
6. **人工验收**：律师看实际界面/行为与业务结果，选择接受、退回或暂停；法律结论/客户外发须明确确认。
7. **交接与版本**：列出变更、版本、证据、未决项、可回退步骤，必要时更新对应 ADR/合同和 Linear Issue；不自动启动下一项任务。

开始执行前先检查 [开源采用矩阵](https://linear.app/logixy-ai/document/研究参考caselite开源架构参考与采用矩阵-v11-c4cdac98fa55)、相关 ADR 与当前 Issue。参考项目的流行度不是技术或许可证明；发现许可证未知、AGPL／商业代码复用、隐性兼容或新增核心框架时，按 `AGENTS.md` 的准入条件停止。

## 3. 一个可复用的任务指令

```text
当前仅处理 Linear Issue：DEV-____。
先只读检查本仓库 AGENTS.md、git status、相关代码及该 Issue，
仅在本 Issue 需要时读取 docs/ 中有关产品、架构、测试或合同的文件。

请先给出：
1. 唯一用户结果和验收方法
2. 修改范围与明确非目标
3. 重要技术/安全风险和需要我决定的事项
4. 将执行的真实命令、失败路径和回退方法
5. 开源参考的来源、许可证及拟复用范围（没有则写「无」）

先运行适用的现有基线；批准范围内再实施最小修改，不得调整无关模块或削弱测试。
按影响范围完成回归；未运行的检查逐项说明原因，不能写成通过。
交付：修改清单、实际检查输出、未执行项、示例/截图（不含秘密）、回退方法。
未经我批准不 push、发布、删除旧数据、修改重要权限或外发资料。
```

## 4. 人工决策的最小表

| 结果 | 判断依据                                    | 下一动作                 |
| ---- | ------------------------------------------- | ------------------------ |
| 接受 | 真实运行，达到用户可见结果和测试/安全要求   | 批准提交/更新任务记录    |
| 退回 | 目标不满足、证据不足或出现回归              | 只修复缺口，补相关测试   |
| 停止 | 数据/权限/费用/法律效果不确定，或不可逆变更 | 暂停并给出候选方案和风险 |

例如：范围和回退清楚、真实命令已找到，可判断「计划可开始」；只看到 AI 自评或模拟结果，判断「证据不足，退回补验」；涉及资料外发、收费、权限或法律结果，判断「需要律师决定，停止等待」。未运行的测试不得写通过，模拟结果不得写联调完成。

验收前再看三件事：LLM 是否把参考代码的热度当作正确性证据，是否把模拟当成真实 Spike，是否通过删除测试或放宽架构检查取得绿色结果；任一项为是，先退回或停止。

## 4.1 常见失败如何处理

| 情形                               | 操作                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| 上下文不足或来源冲突               | 重新读取当前 Issue、仓库文件及必要 Resource；指出具体冲突，暂停依赖该事实的修改。   |
| 编造 API、命令或目录               | 在当前源码、`package.json` 和锁文件中核实；不存在就报告，不以猜测补齐。             |
| 重复模块或过度设计                 | 先搜索旧入口与合同，缩回本 Issue 的最小改动；新增核心依赖或长期协议先走 ADR/Spike。 |
| 命令或 CI 失败                     | 保留原始退出码和日志，定位原因、修复后重跑；不得删除测试或弱化门禁换绿色。          |
| 需要未经授权的联网、代码复用或外发 | 停止相关动作，说明接收方、资料范围、费用和许可证，待律师确认。                      |
| 无法证明完成                       | 列出通过、失败、未运行及缺失证据；退回补验或暂停，不能凭 AI 自评接受。              |

返工仅修复已发现的缺口并重跑相关检查。未提交的错误修改可先核对 `git diff` 后定向 `git restore`；已提交的改动优先用新提交撤销，涉及迁移或用户数据时先按恢复合同处理，不能直接删除旧数据。

## 5. 交接不等于复制聊天

长期技术选择写进 ADR，稳定产品规则在产品/架构资源中，真实代码位置和命令由仓库负责；Issue 状态仍由 Linear 管理。新一轮 LLM 不能依赖“我在上一段聊天解释过”。交接还须写明采用的参考来源、Commit、许可证处理、实际运行和未运行内容及回退点；没有参考代码时明确写「无」。

如果文档与代码不一致，首先查实际迁移、锁文件、运行结果及最新 Linear；明确冲突供人决策，不默默改写现有事实。

## 6. P0 到 P1 门禁

P0 应完成可靠仓库/构建/安全/测试/合成样本、首片实施合同与一次全新会话预演。随后只按律师认可的最近 3—5 个最小功能 Issue 滚动开发；不能把 P0 的“文档已生成”当成 Matter、BYOK、共享或 MCP 的功能验收。

## 7. 代码可读性与独立审查（DEV-1562 / DEV-1564）

1. 开工先实际读取 `AGENTS.md`、`docs/CODE_REVIEW.md`、当前 Issue 和涉及的架构/安全/测试合同；报告已读取路径及适用约束。不要为每段代码创建注释。
2. 先检索已有实现，确认目标包、允许变更和禁止变更；结构、协议、持久化与权限调整须说明 ADR 准入。
3. PR 使用 `.github/PULL_REQUEST_TEMPLATE.md`，填写实际输入输出、关键风险、测试命令及结果、未运行项、回退方法；注释只解释重要的「为什么」。
4. 对安全、IPC、SQLite、PDF 原文定位、Yjs/同步和正式外发等关键变更，安排独立上下文审查；审查者必须阅读 diff、相关合同、实际测试证据，明确发现与剩余风险。审查者的自评不是门禁。
5. 合并前确认自动检查与 GitHub 分支保护真正生效。仅有 workflow 文件或报告不代表 branch protection 已启用；macOS 打包测试不能被 Linux CI 绿色结果替代。
6. DEV-1564 的一次新会话实际交接演练按 `docs/REVIEW_HANDOFF_EXERCISE.md` 执行，留存命令、检查结果及未验证项；不得在演练中生成正式 Matter 产品实现。
