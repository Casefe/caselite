## 三、核心协议不变量（Protocol Invariants）

1. **业务与 Pending 原子提交（Atomic Business + Pending Commit）**：
   本地业务更新与待同步 Mutation 信封必须处于同一个 SQLite 本地事务。数据库提交前不得产生对外持久 ACK；本地失败则 Pending 同样回滚，不留孤儿待发记录。
2. **服务端持久 ACK 与幂等（Durable Server ACK & Idempotency）**：
   服务端接纳密文并写入持久日志后才返回 ACK。同一 `mutation_id` 重复提交 100 次，服务端仅记录一次持久序列，客户端仅产生一次业务应用效果。
3. **回执丢失重查（ACK Loss Resilience）**：
   若客户端发送成功但网络中断导致未收到 ACK，重连后优先以原 `mutation_id` 查询服务端提交状态，已接纳则补发回执，未接纳则安全重传，不产生重复记录。
4. **Pull 应用与 Cursor 推进同事务（Pull & Cursor Atomic Advancement）**：
   增量批次应用与客户端本地已应用 Cursor 推进必须在同一个 SQLite 事务内执行。批次中任意一项校验失败或损坏，整个批次与 Cursor 必须同时回滚，严禁“跳过损坏项并推进游标”。
5. **游标过期与快照恢复（Stale Cursor 410 & Snapshot Recovery）**：
   当客户端 Cursor 落后于服务端日志截断点时，服务端返回 `410 GONE`；客户端自动请求最新签名状态快照，校验根哈希与代次后应用，并随后以快照序列继续拉取增量，不丢失本地未确认修改。
6. **通知丢失兜底（WebSocket Wakeup Loss Fallback）**：
   WebSocket 仅作为实时唤醒通道，送达不等于持久 ACK。客户端断线重连、长时间休眠或通知丢失时，必须具备定时与主动主动拉取（Active Pull）补偿机制。
7. **冲突与拒绝草稿保全（Conflict & Rejection Draft Preservation）**：
   因并发修改版本冲突、服务端拒绝、权限撤销或协议代次不兼容时，客户端必须完整保留用户原始未提交修改为 Pending 状态，禁止静默采用 LWW 覆盖事实，禁止重试超限后自动清除用户草稿。
8. **端到端加密零明文（E2EE & Zero Server Plaintext）**：
   服务端仅作为密文中继与全局定序者，仅能看到账户、设备、密文信封元数据与 key epoch；案情、文书正文与业务字段完全在端侧加解密，服务端不执行明文业务规则校验。
