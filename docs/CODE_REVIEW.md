# CaseLite｜AI 代码可读性与审查规范 v1

> 来源：Linear DEV-1562、DEV-1564；本规范是仓库操作规则，不代替 Linear v2.2 产品/架构/验收资源、实际 Schema、代码、CI 或测试事实。

## 1. 审查目标与优先级

原则：先写清楚代码，注释解释代码难以表达的设计原因。确保不参与开发的新 AI/工程师可以定位实现、理解业务约束、辨认失败路径并安全修改。

审查 diff 时先看测试与 CI 是否被删除或弱化，再看依赖与许可证、迁移与回滚、权限和数据边界，最后检查业务实现；发现无关重构先要求缩小范围。

审查优先关注：**正确性和数据安全 → 模块边界和依赖 → 清晰命名与简单结构 → 失败路径与恢复 → 实际验证证据 → 必要注释与文档**。不得以代码/注释行数、AI 自评或单一覆盖率作为质量指标。

## 2. 最小改动及架构不变量

- 每 PR 原则上一个 Linear Issue 的一项完整目标；开工检索已有模块，避免重复实现及无关重构。若修改跨度扩大，先报告并调整 Issue/ADR。
- UI、内部 Work Runtime、MCP 不得绕过 Application/授权进入 Repository。Electron Renderer 不得接触 Node、任意文件系统、SQLite、密钥；遵守 `docs/ARCHITECTURE.md` 的依赖图。
- 单一权威与版本关系不因局部改动发生暗中变化：本地 SQLite 事务、文件不可变版本、原文 Anchor 与未来 Yjs/同步模型均须遵守相应合同。
- 涉及迁移、进程权限、长寿命协议、关键依赖、同步权威或第三方许可，按 `docs/adr/README.md` 进行决策记录；普通小修不需要 ADR。

## 3. 命名和中文注释

- 函数、变量、类型、目录与协议字段保持准确、统一的英文技术标识；使用已有领域词汇（Matter、SourceVersion、Anchor、Decision 等）。
- **只对 AI 新写、需要解释意图的关键注释使用中文**，重点说明「为何如此、不可破坏的条件、失败时如何处理」。
- IPC/权限/密钥、SQLite 原子事务与回滚、PDF 来源版本/坐标/锚点、未来 Yjs Pending/ACK/同步权威等属于优先注释范围；不是规定每个函数都要写注释。
- 不注释显而易见的代码行为，不用注释掩盖混乱结构。接口语法（如 `@param`）、第三方代码、自动生成代码不为满足中文规则而改写。
- 修改实现时同步更新已失效的重要注释；若注释与代码冲突，以真实代码和测试核实并修复冲突，不能仅删掉不方便的约束。

## 4. 需要逐项审查的风险

| 模块           | 审查不变量和失败路径                             | 验证材料                                   |
| -------------- | ------------------------------------------------ | ------------------------------------------ |
| Electron/IPC   | 发送方、输入 Schema、权限与最小暴露面            | 非法参数/越权负向测试、安全扫描            |
| SQLite/Drizzle | 同事务写入、迁移/回滚、崩溃恢复与旧数据兼容      | 事务故障注入、旧库迁移、重启测试           |
| PDF/Anchor     | 来源版本、页码/旋转/重复文字定位，失配不静默误跳 | 合成 PDF、重复文本/扫描件测试              |
| 编辑器/Yjs     | Y.Doc 权威、Pending 保全、投影不得覆盖原始状态   | 断网/重启/迁移与冲突回归（能力启用时）     |
| Agent/BYOK/MCP | Key、资料外发、权限范围、受控 Effect             | 未授权调用/失败重试/审计证据（能力启用时） |
| P3 同步        | 幂等、ACK、Cursor、撤权、Snapshot 和附件版本     | 双客户端、断网及恢复证据（能力启用时）     |

**未来能力不在 P0 提前实现**；测试与门禁按实际 Issue 范围启用。

## 5. PR 与独立审查

PR 必须包含：Linear Issue、用户结果、变更文件和范围、输入输出、主要失败路径、风险、实际运行的命令/结果、未运行/不适用检查、ADR/文档变更、回退方法。尽量小而完整；测试与实现同 PR，不为压行数省略测试。

关键模块采用独立上下文审查（另一轮 AI 或工程师），依据**实际 diff、代码、架构合同及测试证据**判断；明确列出 blocker、非 blocker 和未验证风险。不让同一 AI 的「我已审查」声明代替审查或合并门禁。

**合并前**：运行适用的 `pnpm check:quick`、`pnpm run ci` 或 `pnpm test:full`；记录不可运行项。Linux CI 不证明 macOS 打包/桌面集成已通过。检查 GitHub 的必需状态检查确已生效；规则未配置时直接说明缺口，不能宣称主分支已保护。

## 6. 新 AI 交接抽检

选一个无真实资料且可回退的示例变更，让不依赖原作者聊天的新 AI：定位模块、说明调用链、说出两个失败路径、找到保护测试、识别植入的违规（如 Renderer→Node 导入、删除测试、削弱 CI）并给出恢复方法。使用 `docs/REVIEW_HANDOFF_EXERCISE.md` 记录证据。该抽检帮助验证规则可发现性，**不能证明所有设计正确**。

## 7. 规则维护

- 根 `AGENTS.md` 仅保存所有任务必读的不变量和指引；本文件解释审查方法，`docs/WORKFLOW.md` 解释操作步骤，`docs/adr/` 保存选择理由，`docs/TESTING.md` 保存具体测试范围。
- `docs/SOURCES.md` 是 Linear 来源索引；产品/架构语义冲突先报告，由有权限者确认，不自行复制与覆写另一份真相。
- 规则、测试、CI 和安全配置属于高风险受保护资产；修改需精确 diff 审查，不得为绿色检查降低门禁。
