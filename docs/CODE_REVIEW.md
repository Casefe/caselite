# CaseLite｜AI 代码可读性与审查规范 v1

> 当前原型执行方式以[WORKFLOW原型直接开发模式](WORKFLOW.md#原型直接开发模式2026-11-05)及2026-11-05用户授权为准。直接在现有开发目录实现，审查对象可以是本地提交/工作树准确Diff；本文中的PR模板、合并前检查及GitHub审批，仅在实际采用对应远端流程时适用，不是本地功能推进的必需形式。保留按实际风险选择的功能/安全检查和必要独立技术复核；不新增每卡用户审阅Git或重复开工确认。

> 来源：Linear DEV-1562、DEV-1564；本规范是仓库操作规则，服从 CaseLite v3.0 [现行01—06](./SOURCES.md)（工程规则按现行06固定ID的实时正文、修订及用户授权核对），不代替批准合同、实际 Schema、代码、CI 或测试事实。

## 1. 审查目标与优先级

原则：先写清楚代码，注释解释代码难以表达的设计原因。确保不参与开发的新 AI/工程师可以定位实现、理解业务约束、辨认失败路径并安全修改。

审查 diff 时先看测试与 CI 是否被删除或弱化，再看依赖与许可证、迁移与回滚、权限和数据边界，最后检查业务实现；发现无关重构先要求缩小范围。

审查优先关注：**正确性和数据安全 → 模块边界和依赖 → 清晰命名与简单结构 → 失败路径与恢复 → 实际验证证据 → 必要注释与文档**。不得以代码/注释行数、AI 自评或单一覆盖率作为质量指标。

## 2. 最小改动及架构不变量

- 一个 PR 服务一个主要 Linear Issue，复杂 Issue 可用少量顺序 PR 检查点，中间 PR 不等于整项验收；开工检索已有模块，避免重复实现及无关重构。若修改跨度扩大，先报告并调整 Issue/ADR。
- UI、内部 Work Runtime、MCP 不得绕过 Application/授权进入 Repository。Electron Renderer 不得接触 Node、任意文件系统、SQLite、密钥；遵守现行02和已核对的仓库架构边界。
- 单一权威与版本关系不因局部改动发生暗中变化：本地 SQLite 事务、文件不可变版本、原文 Anchor 与未来 Yjs/同步模型均须遵守相应合同。
- 涉及迁移、进程权限、长寿命协议、关键依赖、同步权威或第三方许可，按 `docs/adr/README.md` 进行决策记录；普通小修不需要 ADR。

## 3. 命名和中文注释

- 函数、变量、类型、目录与协议字段保持准确、统一的英文技术标识；使用已有领域词汇（Matter、WorkItem、Document、SourceVersion、Anchor 等）。
- **只对 AI 新写、需要解释意图的关键注释使用中文**，重点说明「为何如此、不可破坏的条件、失败时如何处理」。
- IPC/权限/密钥、SQLite 原子事务与回滚、PDF 来源版本/坐标/锚点、未来 Yjs Pending/ACK/同步权威等属于优先注释范围；不是规定每个函数都要写注释。
- 不注释显而易见的代码行为，不用注释掩盖混乱结构。接口语法（如 `@param`）、第三方代码、自动生成代码不为满足中文规则而改写。
- 修改实现时同步更新已失效的重要注释；若注释与代码冲突，以真实代码和测试核实并修复冲突，不能仅删掉不方便的约束。

## 4. 需要逐项审查的风险

| 模块           | 审查不变量和失败路径                             | 验证材料                                   |
| -------------- | ------------------------------------------------ | ------------------------------------------ |
| Electron/IPC   | 发送方、输入 Schema、权限与最小暴露面            | 非法参数/越权负向测试、安全扫描            |
| SQLite/Drizzle | 同事务写入、迁移/回滚、崩溃恢复与旧数据兼容      | 事务故障注入、旧库迁移、重启测试           |
| PDF/Anchor     | 来源版本、页码/旋转/重复文字定位，失配不静默误跳 | 合成 PDF、重复文本/扫描件测试              |
| 编辑器/Yjs     | Y.Doc 权威、Pending 保全、投影不得覆盖原始状态   | 断网/重启/迁移与冲突回归（能力启用时）     |
| Agent/BYOK/MCP | Key、资料外发、权限范围、受控 Effect             | 未授权调用/失败重试/审计证据（能力启用时） |
| 未来同步       | 幂等、ACK、Cursor、撤权、Snapshot 和附件版本     | 双客户端、断网及恢复证据（能力启用时）     |

**未准入能力不提前实现**；测试与门禁按实际 Issue 范围启用。本期 ActivityEvent 不等于未来云 Outbox，不能按旧阶段规划预建。

## 5. PR 与独立审查

开发和 Markdown 修改都须核对基线至当前工作树/提交的准确 Diff、允许文件、合同修订、路径/链接、失败路径、适用检查和未验证项。`review:changes` 已覆盖各级规则Markdown、规则目录及质量配置，删除/清空规则会阻断，内容修订要求独立复核；文档任务仍须检查过期执行规则与虚假能力声明，不能把机器通过当全文正确。

按 [WORKFLOW十二项机制对照](./WORKFLOW.md#十二项开发机制的执行对照)核对适用证据。规则/Skill、模型/权限、检查器变化或同类错误复发时，执行既有独立回归并运行 `pnpm review:changes --require-regression <本轮回归JSON>`；缺失、过期或未通过时不得交付为完成。普通quick的机械通过不代替回归、精准diff审查或业务接受。

| 风险            | 放行要求                                                                                                                             |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 低风险小改动    | 经批准范围、准确 Diff、适用真实检查及回退证据；不以文档扩展业务授权                                                                  |
| 共享接口/跨模块 | 核对唯一 Owner、消费者、兼容与负测；影响结论的后续提交重新审查                                                                       |
| 高风险/未知     | 数据/迁移、原件/Anchor、Yjs/恢复、密钥/权限、依赖/许可证、构建/发布及规则/安全/测试/CI门禁须独立技术复核；未知风险先澄清，不降级放行 |

PR 必须包含：Linear Issue、合同修订/批准范围、baseline/当前被测 SHA（自动化时附 runId）、用户结果、变更文件和范围、输入输出、主要失败路径、风险、实际运行的命令/结果、未运行/不适用检查、ADR/文档变更、回退方法。尽量小而完整；测试与实现同 PR，不为压行数省略测试。

关键模块和受保护规则采用独立上下文审查（另一轮 AI 或工程师）；数据迁移、密钥、备份恢复、共享授权及发布升级等高风险还须针对性的专业工程复核。审查者依据**实际 diff、代码、架构合同及测试证据**判断；明确列出 blocker、非 blocker 和未验证风险。不让同一 AI 的「我已审查」声明代替审查或合并门禁。

**合并前**：运行适用的 `pnpm check:quick`、`pnpm run ci` 或 `pnpm test:full`；记录不可运行项。Linux CI 不证明 macOS 打包/桌面集成已通过。CI 通过不能替代真实 Electron/恢复测试、必要独立审查或律师业务验收。检查 GitHub 的必需状态检查确已生效；规则未配置时直接说明缺口，不能宣称主分支已保护。

自动合并默认关闭，仅适用于本次明确批准且满足白名单、同 SHA 必要检查、适用审查和验收的低风险 Ready PR，细则只见 [WORKFLOW](./WORKFLOW.md)及其专项来源。高风险或未知不自动合并；同一账号的两轮 AI 不是两名 GitHub 审批人。CI/合并不自动触发 Linear“已完成”，不修改规则以绕过要求。

## 6. 新 AI 交接抽检

选一个无真实资料且可回退的示例变更，让不依赖原作者聊天的新 AI：定位模块、说明调用链、说出两个失败路径、找到保护测试、识别植入的违规（如 Renderer→Node 导入、删除测试、削弱 CI）并给出恢复方法。按 [REVIEW_HANDOFF_EXERCISE](./REVIEW_HANDOFF_EXERCISE.md)执行步骤，证据写入现有 Issue/PR；从合同/批准、runId（如有）、HEAD、检查退出码、PR/CI 与恢复检查点续做，不依赖旧聊天。规则更新需新会话核实实际加载；未演练记 `NOT_RUN`。该抽检帮助验证规则可发现性，**不能证明所有设计正确**。

## 7. 规则维护

- 根 `AGENTS.md` 仅保存所有任务必读的不变量和指引；本文件解释审查方法，`docs/WORKFLOW.md` 解释操作步骤，`docs/adr/` 保存选择理由，`docs/TESTING.md` 保存具体测试范围。
- `docs/SOURCES.md` 是 Linear 来源索引；产品/架构语义冲突先报告，由有权限者确认，不自行复制与覆写另一份真相。
- 规则、测试、CI 和安全配置属于高风险受保护资产；修改需精确 diff 审查，不得为绿色检查降低门禁。
