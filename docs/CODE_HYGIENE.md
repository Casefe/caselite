# CaseLite｜代码精简、复用与代码索引规范

> 本规范是开发、独立审查与发布准备的必备工程规则。依据：[DEV-1931](https://linear.app/logixy-ai/issue/DEV-1931)、[现行06](./SOURCES.md#2-六份现行-resources按任务读取)及用户2026-11-15授权；工程规则 Owner 沿 DEV-1562，需求与人工接收 Owner 为谭辉。服从现行合同、[AGENTS](../AGENTS.md)和本轮批准，不授予删除、Git、部署、费用或外发权限。
>
> 代码索引的字段、生成和验收在本文定义，生成器、自动更新、CI接入及自动清理均未实现，记 `NOT_RUN`。执行人员现在仍须在原 Issue／交接中记录本次代码职责、复用判断、清理候选和验证，不得把方案当作索引已经覆盖全仓。

## 1. 目标与治理范围

持续减少缺乏实际价值的实现、重复业务规则和维护成本。重点核对 LLM 为 CaseLite 编写的业务、界面、适配和胶水代码、临时实现与配套说明；人工代码承担相同职责时使用同一判定标准。作者来源本身不是删除依据。

以行为正确、职责清楚、依赖合理和容易维护衡量结果。不设置删行、删文件或依赖数量配额；没有合理删除项的检查可以合格。不通过压缩写法、合并无关职责或削减保护逻辑制造“精简”结果。

保留实际功能以及必要的类型和运行时校验、权限、事务、幂等、错误处理、恢复、审计、测试、构建、配置、许可与操作依据。低频失败路径、没有界面的代码和未被测试执行到的代码，不能因此认定无用。未获准的未来能力也不因本规则预建。

## 2. 复用顺序与成熟组件保护

实现前先检索平台原生能力、项目已有 Application／Port／组件和已准入依赖；确有缺口时才评估新增开源组件。核对功能适配、维护、许可、安全、离线与平台能力、依赖规模、消费者和退出成本；不为少量删行引入更复杂框架。跨稳定边界或核心依赖按现行合同和 ADR／Spike 准入。

成熟框架及开源依赖的内部实现原则上不作业务清理，不修改 `node_modules`，不为未使用某个功能而裁剪上游源码。优先检查 CaseLite 自建的多层包装、重复转换、缓存和状态；仍承担权限、协议、事务、版本或失败恢复职责的适配必须保留。

完全不用的依赖可在另一个明确获准范围内整体移除，先检查脚本、构建、插件、Peer／可选依赖及动态加载，完成适用打包和运行验证。第三方源码复用、升级和移除仍沿 [开源采用入口](./SOURCES.md#3-工程规范与专项工作的唯一入口)和 [ADR-005](./adr/ADR-005-third-party-code-license-and-clean-room.md)；本文不新增任何工具或依赖准入。

代码保护与受控变更的唯一细则见[CODE_PROTECTION](./CODE_PROTECTION.md)：资产等级/动作裁决、未知消费者、源码与执行副作用、稳定候选及恢复断言沿该规范；本文继续拥有精简/复用治理和索引方案，不由索引生成授权或降低保护。两份规范的机械覆盖限制与额外hash/精准Diff/独立回归均须遵守，不重复维护保护规则全文。

## 3. 清理判定与保留依据

每个候选记录实际位置、原职责、替代或不再需要的证据、所有已知消费者、未知项、影响、测试和回退。证据不足先保留并回原 Owner 核实，不自动删除。

| 对象                       | 可以进入删除／合并候选的条件                                   | 必须核对的失败路径                                                                                       |
| -------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 重复实现                   | 业务语义一致且已有唯一实现可承担全部实际消费者                 | 权限、校验、事务、错误与取消、重复提交、未知回执、重开；不把相似表单强并成通用 CRUD                      |
| 无用文件／导出／样式／配置 | 实际入口与消费者核实后确实不需要                               | 动态导入、字符串注册、IPC、Worker、插件、构建／资源路径和平台条件                                        |
| 临时补丁／开关／调试       | 根因修复或需求撤销有证据，回退不再依赖它                       | 隐性配置、失败恢复、缓存与启动路径；必要可观测性不能一并删除                                             |
| 预建抽象／占位能力         | 没有获准需求与实际消费者，移除不破坏现行合同                   | 生成／注册机制及已获准但尚未接合的候选；不得将冻结需求视为取消                                           |
| 旧版本兼容层               | 从未发布且无真实消费者，或支持范围已明确撤销并有迁移／恢复方案 | 本地旧库、导入文件、备份、正文／原件版本、Anchor 和已保存修订                                            |
| 历史说明文档               | 已失效或重复，独有有效内容已迁入唯一入口                       | 架构理由、ADR状态、许可、恢复方法、验收证据、未完成需求及入链引用                                        |
| 测试                       | 对应需求已正式撤销，或有等效／更强行为保护并获得审查           | 不删失败断言、不放宽门禁，遵守既有删测阻断与 [测试价值审计](./TESTING.md#测试价值审计与性能测量dev-1924) |

静态工具报告、覆盖率为零、文件年龄和 Git 搜索结果都只是线索；不可达性和业务必要性须分别核实。没有静态引用不证明没有消费者；未知消费者不得默认填“无”。Knip 等仅为候选，不因文中列名自动安装、执行自动修复或授予许可例外。

新产品仍可能已有需要保护的数据。迁移历史、SQLite、Yjs 正文、AssetVersion／SourceVersion、Anchor 和恢复路径不因“旧版”命名可删。禁止重置数据来证明成功，禁止将旧程序可运行等同于它能打开新库；需要改变支持范围时先交相应 Owner 决定。

历史文档先核对独有证据和引用；必要内容迁至原 Owner 的现行唯一入口，修复链接。已被替代的 ADR 保留决定轨迹并标状态；许可证、NOTICE 与必要恢复依据受保护。未提交或未跟踪内容先保存可恢复副本，不假定 Git 已保存它。本轮 DEV-1931 只建立规则和方案，不执行这些删除。

## 4. 日常与发布前流程

| 时机                  | 必须执行的动作                                                                 | 留证位置                                                 |
| --------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------- |
| 每个 Issue 开工与交付 | 检索已有实现；审查本次新增重复、临时分支和封装，说明保留／候选理由             | 原 Issue 的范围、准确 Diff 和既有交接字段                |
| 开发期间每周          | 汇总候选并由 Owner 按风险决定有界批次；无候选如实记录                          | 既有工程 Issue／证据，不建周报或任务数据库               |
| 每个发布候选冻结前    | 对准确候选完成精简审查、适用回归与未决项处置；未解决影响发布的风险须有明确决定 | 既有发布 Issue、同候选 SHA／工作区快照、包哈希与验证证据 |
| 冻结后仍有变化        | 重新核对受影响行为、索引和证据，不能沿用已失效结论                             | 原发布记录中的增量证据                                   |

周期规定是人工／代理执行责任，不代表已安装自动定时任务，也不解除当前旧队列冻结。扫描与候选记录不自动授权删除或新开工；执行清理须另有明确获准 Issue／范围、单写入槽和适用依赖。

每个获准清理批次遵循：

1. 明确唯一用户结果、Owner、允许文件、保留行为、风险、基线和回退；先保存既有未提交内容，保护并行工作。
2. 清理前建立有效的测试基线；仅在代码、规则、依赖和环境仍适用时复用已有证据。关键行为缺保护先补必要测试；基线失败先定位，不以删除实现或测试消除红色。
3. 小批变更，保持既定外部行为；功能撤销、支持范围或法律／业务语义改变按需求变更处理。
4. 清理后执行现有 `pnpm check:quick`、`pnpm review:changes`，按影响补集成、安全、构建、真实桌面和恢复；记录命令、退出码、准确快照、未测与不适用原因。涉及公开资料、日志、依赖或桌面边界至少执行 `pnpm security:baseline`。测试遵守 [静默与批次授权](./WORKFLOW.md#静默测试与批次授权)。
5. 另一独立 Sol High 上下文对照需求、准确 Diff、消费者、失败和恢复证据审查。规则／模型／权限／检查器变化按 [独立回归](./REVIEW_HANDOFF_EXERCISE.md)实跑，完成带回执交付检查；AI自评或普通quick不能代替。
6. 更新原 Issue 交接及可用索引，分别记录 `PASS_REAL/MOCK_ONLY/NOT_RUN/BLOCKED/FAIL`。测试失败、消费者不明或恢复证据不足时停止对应删除、保留现场并回 Owner，不扩大范围。

回退须明确本轮新增、修改及删除文件的恢复方式、未提交前像和验证步骤。代码回退不等于数据恢复；数据变化沿现行数据与恢复合同，不执行批量 reset／clean／restore 覆盖其他工作。Git commit、push、merge 分别取得现行授权，规范本身不授予这些动作。

## 5. 代码索引方案：覆盖与唯一来源

目标是使受管代码每一行都能定位到其文件、职责块、来源与可信变更记录。人工维护文件／函数／代码块的功能与必要性，机器根据语法范围生成行映射；不要求逐行人工注释或把语法括号编造为业务功能。

生产源码、胶水、脚本、样式、配置、测试及受管生成文件均进入文件清单，分类后记录处理方式；文档进入引用／职责清单。第三方安装目录、可重建产物、密钥和用户数据排除，排除规则必须有理由与覆盖计数。供应的第三方源码以来源、版本、许可和文件校验记录，不逐行改写其内部含义。

代码／锁文件说明真实实现，Git提供提交历史，Linear提供需求、Owner和验收，ADR提供长期决定。索引只是这些来源的可重建投影，不接管任务状态、需求、正文、权限或开发队列，不新建数据库／Runtime／常驻服务。功能说明无法可靠推导时使用现有代码块关键说明或原 Issue 的稳定引用，人工核对含义；新增元数据不复制任务全文。

建议产物为本机 `artifacts/code-index/` 下的 manifest、记录和行映射，后续实现前须验证忽略与排除规则；公开仓库仅保留本文方案和获准的非敏感结构。生成器未落地期间在现有交接记录必要元数据，不要求先人工补全全仓才能普通开发，也不宣称完成逐行覆盖。

### 5.1 记录结构与定位

| 层级／字段   | 定义与约束                                                                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| manifest     | `schemaVersion`、生成器版本／配置哈希、生成时间、仓库相对标识、`headSha`、规则指纹、受管路径／排除规则、快照清单哈希、覆盖统计、未解析／失败项       |
| 文件快照     | 仓库相对路径、文件字节 `sha256`、总行数、语言／分类、tracked／untracked／deleted、是否未提交、采集前后校验；时间使用含时区格式                       |
| 职责块       | 快照内块ID、文件路径、符号／限定名、类型、行起止（1起算且含末行）、职责摘要、必要性理由及依据链接；嵌套块声明父子关系                                |
| 逐行映射     | 文件快照到职责块ID；重复覆盖选择最内层块并保留父链。顶层语句／导入／样式与配置段归明确块，注释／空行／括号可归最近结构块或语法块，不虚构独立业务语义 |
| 需求与责任   | 原 Issue 稳定ID／链接、领域／工程 Owner、适用合同／ADR及实际读取修订；缺失为 `UNKNOWN`，不把Git作者自动当业务Owner                                   |
| 来源         | 自研人工／LLM辅助／第三方／生成／未知；证据链接，第三方版本／Commit／许可，生成代码的输入与生成器；实际模型、人工修改范围仅在有可信回执时填          |
| 时间与历史   | 可核实首次引入的提交与提交时间、最后相关修改提交与提交时间、快照采集及索引生成时间分别记录；提交时间不是精确编写时间，文件mtime不是来源证明          |
| 消费者与边界 | 静态调用方与采集方法、动态／平台入口及人工核实依据、外部契约与副作用；完整性／未知项明确标记，不将空数组解释为“无消费者”                             |
| 验证         | 保护行为、测试位置、实际命令／退出码、证据位置及hash、被验证代码快照与环境；只有匹配快照且适用的证据可标通过，缺失为 `NOT_RUN`                       |
| 治理标记     | 保留／待核实／待合并／待删除、理由和决定依据；只是由原Issue决定派生的候选，不是执行授权或Issue状态                                                   |

Git blame只提供行级最后修改的提交信息；首次引入需结合历史，重命名／复制／移动可能存在歧义。无充分证据时记 `UNKNOWN`，不得由代码风格推测作者、LLM模型或创建时间。未提交内容记录快照采集时间、工作区差异与可得作者回执；不得借HEAD提交时间代表新代码时间。

块ID仅在给定快照内有效。跨快照跟踪采用符号、内容指纹和Git移动／重命名证据，保留旧／新路径关系；候选匹配有歧义须待核实，不能保证符号改名后仍是同一块。文件或符号删除留历史快照引用及删除依据，当前索引不得继续显示为在用。

### 5.2 生成、更新与失效

后续生成器优先复用当前仓库已有 TypeScript 解析能力及Git工具。CSS、JSON、Markdown等用实际可用解析或保守结构块，不为索引提前引入另一套解析平台；无法识别的文件保留文件级范围和 `UNKNOWN`，不得静默漏掉。

以完整文件清单和字节哈希定义一次快照，`headSha`不能单独代表混合工作区。采集前后文件内容或清单变化则该快照失败／待重建，不能发布半新半旧结果。文件名排序、相对路径和哈希算法必须确定；索引生成时间不纳入内容一致性比较。

源码、未提交／未跟踪内容、符号、路径、生成输入、排除配置、解析器或模式变化，使相关记录失效；消费者、Issue决定或证据修订变化也须重新核对，不能只按源码mtime判断。增量更新重算变化文件及受影响消费者／行映射，合并到新快照前核对完整清单；周期或发布前做一次全量对账，发现缺漏不得标全量有效。

使用者读取前核对快照、文件hash、生成配置、来源和适用证据。失配、未解析或部分失败时明确显示未知／失效，禁止据此自动删除、跳过验证或声称每行已覆盖。删除全部索引后应能从批准输入重建；丢失索引不丢源码、业务数据、批准或历史证据。

功能与必要性摘要由责任人审校；LLM可辅助整理但不能独自证明业务语义、无消费者或删除安全。索引中的人员、内部Issue内容、路径和证据链接也可能敏感；最少采集、仅本地默认保存，不收集源码副本、客户材料、密钥、环境变量值、绝对用户路径或原始敏感日志。上传或公开索引按既有外发与公开仓库规则另行核对。

### 5.3 后续实现验收样例

以下是生成器后续准入与验收要求，本轮均未运行；不得把本文样例写成已通过测试。

| 场景                                       | 必须观察到的结果                                                             |
| ------------------------------------------ | ---------------------------------------------------------------------------- |
| 含嵌套函数、顶层配置、注释与空行的合成文件 | 清单及总行数一致，每行可定位职责／结构块；未知语义明确，覆盖计数不靠忽略提高 |
| 在HEAD后插行、修改及新增未跟踪文件         | 新hash／行映射匹配实际工作区，未提交时间不冒用HEAD，旧证据不能自动通过       |
| 文件移动、符号改名、重复内容复制与删除     | 当前路径可追溯，歧义待核实；删除对象不留作当前消费者，历史证据仍可定位       |
| 字符串IPC、Worker和动态插件无静态导入      | 显示动态入口／未知消费者并保留候选，不能自动认定死代码                       |
| 生成期间文件变化或解析失败                 | 拒绝完整成功声明，显示失败／失效项，重建后再核对                             |
| 只有旧测试证据、缺少来源或模型回执         | 分别显示快照不匹配、`UNKNOWN`或`NOT_RUN`，不猜测首次编写时间与模型           |
| 排除依赖／生成目录并放入合成秘密诱饵       | 排除理由与计数可查，无秘密值或源码副本进入索引；清理索引后仍可重建           |

## 6. 交付与机械门禁的实际边界

交付沿现有 Issue／模板记录范围、文件、合同修订、SHA／工作区快照、复用与保留理由、候选及消费者不确定性、清理前后命令和退出码、失败／恢复、未测、独审与回退。规则变更使用真实独立新上下文回归，不把指令文件当成宿主强制执行证据。

当前 `scripts/check-quality-changes.mjs` 的规则指纹与受保护规则列表没有直接覆盖 `docs/CODE_HYGIENE.md`。相关AGENTS／WORKFLOW引用变化会触发既有回归，但仅有 `rulesSha256`不能证明本文版本已被审查。本文新增或修改须额外保存文件SHA-256、准确Diff及本轮候选快照，由独立审查核对；后续单独修改本文也不得以检查器未触发为由免除规则回归。检查器正式接入需另行获准实现与负向回归，本轮不更改它。

本规范只采用方法，没有复用第三方源码：小步保持外部行为参考 [Refactoring](https://refactoring.com/)，静态分析误报与动态入口参考 [Knip指南](https://knip.dev/guides/handling-issues)，行级历史能力参考 [Git blame](https://git-scm.com/docs/git-blame)。工具输出、规则存在、静态方案和真实产品运行分别验收。
